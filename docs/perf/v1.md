### Before and after the name index

M1-19 measured 10,000 small files in at 44 minutes, each new file listing its whole folder (`spikes/m1-exit.md` §4). With the names of a folder kept up to date in place (spec §5.6), the same copy takes 158 s, and the cost per file no longer grows with the folder: 14.0 ms a file for 1,000 files, 15.8 ms for 10,000.

### The relaxed NFR-PERF-07 and its cheap steps

The owner relaxed NFR-PERF-07 to ≤ 3× `scp -r` (§3, item 1, choice a), and two steps followed:

- **No fsync when a file is closed.** `Cleanup` no longer calls `fsync@openssh.com`; `Flush` (`FlushFileBuffers`) still does (spec §5.6).
- **Answers kept.** What `set_attr` and `fstat` return is kept as the path's attributes, as a `stat`'s would be, unless the path changed meanwhile or the handle's file lost its name (spec §5.6). `stat` calls went from 4.8 to 2.8 a file, and robocopy opens each file 6 times instead of 15.

LAN went from 158 s to 90 s (ratio 5.53 to 2.90). The measurements in the next table are from before these steps.

| Remote call (after) | Per file | Each, LAN | Each, WAN |
|---|---|---|---|
| `set_attr` | 3 | 1.33 ms | 69.0 ms (~2.7 round trips) |
| `stat` | 2.8 | 0.54 ms | 25.9 ms |
| `fstat` | 2 | 0.49 ms | 25.9 ms |
| `open`, `write`, `close` | 1 each | ~0.6 ms | ~26 ms |

On WAN, `set_attr` is the largest cost. It reads the current attributes first when it has to (for the read-only bit, or one time without the other), then `setstat`, then reads the result. Pipelining these would save ~40 s of the 115 s; see §3.

## 3. What is open, for the owner

1. **Decided: NFR-PERF-07 relaxed to ≤ 3× (choice a), and both cheap steps done.** LAN meets it at 2.90, with little margin. The owner then set the budget for LAN only, so WAN's 3.58 is for information. Should WAN ever matter, the next cheap step is to send `set_attr`'s `setstat` and the `stat` after it together (and the `stat` before, when it can be avoided). That relies on the server handling requests about one file in order, and a wrong answer would now be cached. The text below is how the decision was put.
   **NFR-PERF-07 cannot be met by tuning.** Without the `fsync` at Cleanup a file would cost ~9 ms, still ~3× `scp`. Reaching 1.3× needs about 5 round trips a file, which means answering Windows without waiting for the server on metadata too (attributes set and files closed in the background, errors reported later, as with write-behind). That is a design change with a real cost in error reporting. Choices:
   - **a.** Relax NFR-PERF-07, for example to ≤ 3× `scp -r`, and do the cheap steps below.
   - **b.** Keep it, and design asynchronous creates, attribute changes and closes (a new ADR).
   - **Cheap steps either way:** drop the `fsync` at Cleanup and keep it at Flush (Windows' own meaning of `FlushFileBuffers`; a closed file is not promised to be on disk), which is spec §5.6's rule today, so it needs the owner too; keep the attributes that `set_attr` and `fstat` return, rather than asking again.
   - **Tried and dropped:** the `fsync` at Close instead of Cleanup. Programs then opened each file ~30 times while it ran, for the same total time.
2. **Done: NFR-PERF-06 writes on WAN,** with the bounded write-behind (OD-4, [ADR-0002](../adr/0002-write-behind.md)): 4.16 → 1.02 of `sftp put`. The file copied back is compared byte for byte. Small files gain too: the `fstat` after each write is gone (2 → 1 a file), and LAN went to 2.87. The owner should know what it gives up: a write's failure is heard one call later (the next `Write` or `Flush`), or only in the log by a program that never calls again.
3. **NFR-PERF-01, 02, 04, 05 and 10 are not measured yet,** nor Explorer itself for NFR-PERF-09.

## 2. How to measure again

```bash
tests\docker\servers.ps1 up
```

```bash
DRIVEMOUNT_TEST_HOST=172.23.105.89 cargo test --release -p drivemount --test perf -- --ignored --nocapture --test-threads=1
```

The address is the WSL VM's, from `wsl hostname -I`. Each line starting `PERF |` is one measurement; `PROFILE |` lines break the small-files copy down by WinFsp callback and by remote call.

- **WAN:** `PERF_DELAY_MS=25` adds 25 ms each way with netem on the WSL VM's `eth0` (50 ms of round trip, as §4.1 says) and removes it afterwards. It needs `wsl -u root`.
- **Smaller runs:** `PERF_SMALL_FILES` (default 10,000) and `PERF_LARGE_MIB` (default 1024).
- **What each test does:**
  - `nfr_perf_06_one_large_file`: `CopyFileExW` (what Explorer uses) to the drive, unmount, mount, and back; against `sftp`'s `put` and `get` with its login time taken off.
  - `nfr_perf_07_ten_thousand_small_files`: `robocopy` of 4 KiB files into a new folder; against `scp -r`.
  - `nfr_perf_08_and_09_listings`: a folder of 1,000 entries made on the server, listed with attributes on a fresh mount, then again; and the root of a fresh mount. The root listing stands in for NFR-PERF-09: Explorer itself is not driven.
- **Profiles:** the WinFsp callbacks are `callback` spans at Debug and every remote call a `remote` span at Trace (`drivemount-winfsp`'s `Adapter::run` and `drivemount-vfs`'s `DeadlineFs`), so any `tracing` subscriber can see where time goes. This is also how NFR-PERF-10 is to be checked for the file system side.
