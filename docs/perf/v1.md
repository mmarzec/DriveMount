The spec's environment is a separate Linux server on 1 GbE. Here the server is a VM on the same PC, so the "LAN" round trip is about 0.5 ms and the disk is a virtual one inside WSL. Absolute times are only indicative; the ratios to OpenSSH, measured on the same link at the same time, are what the budgets ask for.

### 1.1 Start-up (NFR-PERF-01, 02)

The app logs `since_start_ms`, counted from the process's creation time (`GetProcessTimes`), at the first frame drawn (`the first frame is drawn`) and when the shell takes the tray icon (`the icon is in the tray`). Slint's software renderer has no rendering notifier, so the first frame is taken from winit's first `RedrawRequested`, logged from a closure posted behind it, after Slint has drawn.

The starts are warm: the exe is in the file cache after the first. A start right after a freshly built exe was 253 ms, and starts right after other work (a `wsl` call) were 224–331 ms, so the margin is small on a loaded machine, as at sign-in. Where the time goes in one start (ms since the process was created):

| Step | Until |
|---|---|
| Process, DLLs, config and log open | ~30 |
| Runtime and window made | ~45 |
| Engine and manager | ~55 |
| Tray icon in (waits for Explorer) | 78–122 |
| Toasts, single-instance listener, `show` | +7 |
| First frame (winit window and first software render) | 177–236 |

The ~95 ms from the event loop starting to the first frame is the largest share, in winit and Slint; Slint's system-font lookup is a likely part. Showing the window before waiting for the tray would save 20–65 ms on a window start (§3).

### 1.2 The UI thread (NFR-PERF-10)

`app::ui_clock` times each stretch the UI thread is kept busy: from winit handing the window an event to the event loop getting to a closure posted then (Slint's handling, the redraw it caused and anything queued behind it), and each action other threads post. A stretch over 16 ms is logged at Debug (`the UI thread was busy for longer than a frame`), and the longest at quit (`the UI thread's longest busy stretch`). Network and file system work is never on the UI thread by design (engine, actors, WinFsp threads), so this measures drawing and the window's own logic.

`nfr_perf_10_ui_thread` mounts five drives with *Mount all*, opens and cancels *Add connection*, goes to *Settings* and back, maximizes and restores the window and unmounts all, twice. Three runs: longest 15.5, 17.9 and 17.6 ms, each time a redraw. With the threshold lowered to 4 ms, the timeline showed one 17.6 ms redraw ~1 s after the window took focus, when *Mount all* turned five rows to *Connecting*; every other redraw was ≤ 12.9 ms, maximized included, and focus took 12.8 ms. So it is the first draw of new content (new text and icons), once a session. Showing the window from the tray also drew one stretch over 16 ms.

### 1.3 Explorer (NFR-PERF-09)

Opening a new Explorer window costs ~1.2 s on this machine for any folder, a local one too, so `nfr_perf_09_explorer_opens_the_drive` opens a window on *This PC* first, then navigates it to the drive's root (`Navigate2`, as a double-click on the drive does) and polls UI Automation until `perf-1.txt` is listed. The root holds 100 files, made on the server for the test. Each round, a new `drivemount.exe` mounts the drive at start just before; the same root is then opened again (from the cache), and a local folder of 100 files for comparison.

| | Median | Range |
|---|---|---|
| Fresh mount's root | 380 ms | 372–629 ms |
| Same root again | 380 ms | 366–432 ms |
| Local folder, 100 files | 424 ms | 377–431 ms |

The polling itself (a UI Automation search of the window every few ms) is part of every figure, which is why the local folder is no faster. One fresh round took 629 ms; the others were within 81 ms of the local folder.

### Before and after the name index

M1-19 measured 10,000 small files in at 44 minutes, each new file listing its whole folder (`spikes/m1-exit.md` §4). With the names of a folder kept up to date in place (spec §5.6), the same copy takes 158 s, and the cost per file no longer grows with the folder: 14.0 ms a file for 1,000 files, 15.8 ms for 10,000.

### The relaxed NFR-PERF-07 and its cheap steps

The owner relaxed NFR-PERF-07 to ≤ 3× `scp -r` (§3, item 1, choice a), and two steps followed:

- **No fsync when a file is closed.** `Cleanup` no longer calls `fsync@openssh.com`; `Flush` (`FlushFileBuffers`) still does (spec §5.6).
- **Answers kept.** What `set_attr` and `fstat` return is kept as the path's attributes, as a `stat`'s would be, unless the path changed meanwhile or the handle's file lost its name (spec §5.6). `stat` calls went from 4.8 to 2.8 a file, and robocopy opens each file 6 times instead of 15.

LAN went from 158 s to 90 s (ratio 5.53 to 2.90). The measurements in the next table are from before these steps.

| Remote call (after) | Per file | Each, LAN | Each, WAN |
|---|---|---|---|
| `set_attr` | 3 | 1.33 ms | 69.0 ms (~2.7 round trips) |
| `stat` | 2.8 | 0.54 ms | 25.9 ms |
| `fstat` | 2 | 0.49 ms | 25.9 ms |
| `open`, `write`, `close` | 1 each | ~0.6 ms | ~26 ms |

On WAN, `set_attr` is the largest cost. It reads the current attributes first when it has to (for the read-only bit, or one time without the other), then `setstat`, then reads the result. Pipelining these would save ~40 s of the 115 s; see §3.

### Where a small file's time goes (LAN, 10,000 files, before the cheap steps)

| Remote call | Per file | Each | Why |
|---|---|---|---|
| `flush` (`fsync@openssh.com`) | 1 | 5.2 ms | Cleanup. Of this, ~4 ms is the server's disk: 200 × 4 KiB with `dd conv=fsync` took 5.2 ms each in the container, against 1.3 ms without. |
| `stat` | 4.8 | 0.66 ms | robocopy opens each file ~15 times (`get_security_by_name`, `open`, `close` all ~14–15 per file); each write or attribute change drops the file's cached attributes, and each new name its folder's. |
| `set_attr` | 3 | 1.35 ms | `SetFileSize`, and `SetBasicInfo` twice; each is a `setstat` and a `stat` for the answer. |
| `fstat` | 2 | 0.49 ms | One after the create, one after the write. |
| `open`, `write`, `close` | 1 each | ~0.6 ms | |

About 14 round trips a file. `scp` streams, at ~2.9 ms a file here.

## 3. What is open, for the owner

1. **Decided: NFR-PERF-07 relaxed to ≤ 3× (choice a), and both cheap steps done.** LAN meets it at 2.90, with little margin. The owner then set the budget for LAN only, so WAN's 3.58 is for information. Should WAN ever matter, the next cheap step is to send `set_attr`'s `setstat` and the `stat` after it together (and the `stat` before, when it can be avoided). That relies on the server handling requests about one file in order, and a wrong answer would now be cached. The text below is how the decision was put.
   **NFR-PERF-07 cannot be met by tuning.** Without the `fsync` at Cleanup a file would cost ~9 ms, still ~3× `scp`. Reaching 1.3× needs about 5 round trips a file, which means answering Windows without waiting for the server on metadata too (attributes set and files closed in the background, errors reported later, as with write-behind). That is a design change with a real cost in error reporting. Choices:
   - **a.** Relax NFR-PERF-07, for example to ≤ 3× `scp -r`, and do the cheap steps below.
   - **b.** Keep it, and design asynchronous creates, attribute changes and closes (a new ADR).
   - **Cheap steps either way:** drop the `fsync` at Cleanup and keep it at Flush (Windows' own meaning of `FlushFileBuffers`; a closed file is not promised to be on disk), which is spec §5.6's rule today, so it needs the owner too; keep the attributes that `set_attr` and `fstat` return, rather than asking again.
   - **Tried and dropped:** the `fsync` at Close instead of Cleanup. Programs then opened each file ~30 times while it ran, for the same total time.
2. **Done: NFR-PERF-06 writes on WAN,** with the bounded write-behind (OD-4, [ADR-0002](../adr/0002-write-behind.md)): 4.16 → 1.02 of `sftp put`. The file copied back is compared byte for byte. Small files gain too: the `fstat` after each write is gone (2 → 1 a file), and LAN went to 2.87. The owner should know what it gives up: a write's failure is heard one call later (the next `Write` or `Flush`), or only in the log by a program that never calls again.
3. **Decided: NFR-PERF-10's one slow redraw is accepted (choice a).** The text below is how it was put. It is missed by ~2 ms, once a session: the first redraw after *Mount all* (17.6–17.9 ms; §1.2). Everything else is within 16 ms. Choices:
   - **a.** Accept it: a one-time 18 ms frame is not felt, and the budget is about the UI never waiting on work.
   - **b.** Look into it with a profile (Windows Performance Recorder) of that redraw: likely glyphs and icons drawn for the first time; drawing them once at start, hidden, may move the cost into the start-up (which has ~10 ms of margin).
4. **NFR-PERF-01 has little margin:** max 240 ms of 250 on a quiet machine, up to 331 ms right after other work (§1.1). If it needs more room: show the window before waiting for the tray icon (saves 20–65 ms on a window start; a `--tray` start is unchanged), and profile winit's first frame. Not done here, as it is met as measured.
5. **NFR-PERF-09: one round of five took 629 ms.** The others matched a local folder. Not followed up.
6. **NFR-PERF-05: both 10-minute windows came out at exactly 141 ms of CPU.** Plausible, as idle work is keep-alives on a fixed timer, but worth a second run if it matters.

## 2. How to measure again

```bash
tests\docker\servers.ps1 up
```

```bash
DRIVEMOUNT_TEST_HOST=172.23.105.89 cargo test --release -p drivemount --test perf -- --ignored --nocapture --test-threads=1
```

The address is the WSL VM's, from `wsl hostname -I`. Each line starting `PERF |` is one measurement; `PROFILE |` lines break the small-files copy down by WinFsp callback and by remote call.

- **WAN:** `PERF_DELAY_MS=25` adds 25 ms each way with netem on the WSL VM's `eth0` (50 ms of round trip, as §4.1 says) and removes it afterwards. It needs `wsl -u root`.
- **Smaller runs:** `PERF_SMALL_FILES` (default 10,000) and `PERF_LARGE_MIB` (default 1024).
- **What each test does:**
  - `nfr_perf_06_one_large_file`: `CopyFileExW` (what Explorer uses) to the drive, unmount, mount, and back; against `sftp`'s `put` and `get` with its login time taken off.
  - `nfr_perf_07_ten_thousand_small_files`: `robocopy` of 4 KiB files into a new folder; against `scp -r`.
  - `nfr_perf_08_and_09_listings`: a folder of 1,000 entries made on the server, listed with attributes on a fresh mount, then again; and the root of a fresh mount. The root listing stands in for NFR-PERF-09: Explorer itself is not driven.
- **The app's own budgets** (`apps/drivemount/tests/perf_app.rs`, the real release `drivemount.exe` under a scratch `APPDATA`, `LOCALAPPDATA` and `USERPROFILE`; your own DriveMount must not be running, as a release build has the real single-instance name):

```bash
DRIVEMOUNT_TEST_HOST=172.23.105.89 cargo test --release -p drivemount --test perf_app -- --ignored --nocapture --test-threads=1
```

  - `nfr_perf_01_02_start_times`: `PERF_STARTS` (default 10) starts each, with and without `--tray`, with no profiles and with five, read from the log.
  - `nfr_perf_04_05_memory_and_idle_cpu`: the working set after 60 s, then CPU time over `PERF_IDLE_SECS` (default 600) with five drives, hidden then shown. Over 20 minutes.
  - `nfr_perf_09_explorer_opens_the_drive`: as in §1.3, `PERF_STARTS` rounds (default 5).
  - `nfr_perf_10_ui_thread`: as in §1.2.
  - The drives are `keyonly` on S-03 with the test key, its host key read from the container into `known_hosts`. WSL stops its containers once nothing runs in it: keep a `wsl -d Ubuntu-22.04 -- sleep 7200` going.
- **Profiles:** the WinFsp callbacks are `callback` spans at Debug and every remote call a `remote` span at Trace (`drivemount-winfsp`'s `Adapter::run` and `drivemount-vfs`'s `DeadlineFs`), so any `tracing` subscriber can see where time goes. The UI thread has its own clock (§1.2).
